HTTP SOCKET PROGRAMMING ZERO-CLOUD SUBNET

ESP32 Socket-Level Local HTTP Server & Hardware GPIO Actuation

Microcontroller-hosted HTTP web server executing native TCP socket listening for direct, zero-latency local subnet hardware control and real-time GPIO state toggling.

Assignment Objective & Problem Addressed

Objective: Design, configure, and deploy an autonomous, bare-metal embedded HTTP web server on the dual-core ESP32 System-on-Chip (SoC) to execute zero-latency local Wi-Fi browser actuation of a digital LED/relay actuator, operating entirely decentralized without external internet dependencies or third-party cloud brokers.

Problem Addressed: Standard cloud-reliant IoT architectures introduce fatal failure points: external WAN latency, periodic vendor outages, subscription API fees, and catastrophic loss of local appliance control during internet dropouts. This module establishes a deterministic, fail-safe edge control plane by hosting native TCP socket listeners on standard Port 80 directly inside the ESP32 SRAM.

Browser-to-ESP32 Wi-Fi Communication Protocol Flow

  • 1. Station (STA) Network Association: ESP32 negotiates WPA2-PSK authentication with the local Wi-Fi router, obtaining a local subnet IP (e.g., 192.168.1.105) via DHCP.
  • 2. Native Port 80 Socket Binding: WebServer server(80) instantiates a non-blocking TCP socket listener monitoring incoming SYN packets on standard HTTP port 80.
  • 3. HTTP GET Dispatch & Route Parsing: Client browser sends an HTTP/1.1 GET /relay/on request. The ESP32 parses the request line and triggers registered lambda handler server.on("/relay/on", ...).
  • 4. Register-Level GPIO Actuation: The handler executes digitalWrite(RELAY_GPIO, HIGH), shifting the hardware output register and forward-biasing the LED.
  • 5. HTTP 303 Redirect & UI Re-render: The ESP32 returns an HTTP 303 See Other response redirecting the browser back to /, which dynamically serves the refreshed HTML control interface.
🛠️ PROBLEMS ENCOUNTERED & ENGINEERING SOLUTIONS (CLICK TO EXPAND) ▼
Problem 1: Wi-Fi Reconnection Freezes & TCP Socket Drops

During transient router signal drops or DHCP lease renewals, blocking Wi-Fi reconnect routines inside loop() halted the single-threaded web server, freezing UI responsiveness and dropping active HTTP connections.

ENGINEERING FIX Implemented a non-blocking background connection monitor in loop() checking WiFi.status() != WL_CONNECTED with exponential backoff timers, preserving continuous socket listening without freezing the microcontroller core.
Problem 2: Dynamic DHCP IP Shifting Requiring UART Discovery

Every router reboot leased a new dynamic IP address to the ESP32, forcing the engineer to reconnect the USB cable and open the serial monitor to discover the updated web server address.

ENGINEERING FIX Integrated Multicast DNS (ESPmDNS.h) broadcasting the persistent local hostname http://esp32-webserver.local, enabling seamless zero-configuration browser access from any subnet device without manual IP lookup.
💡
Final Learning Reflection: Building a bare-metal HTTP server revealed how transport-layer TCP sockets interact directly with application-layer HTTP protocols on embedded silicon. Eliminating cloud middlemen guarantees sub-10ms response latency and absolute data sovereignty, proving that local edge servers are vital for mission-critical industrial actuators where internet uptime cannot be guaranteed.

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_GPIO, OUTPUT);
  digitalWrite(RELAY_GPIO, LOW);
  
  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.printf("\nNode Connected! Subnet IP: %s\n", WiFi.localIP().toString().c_str());

  if (MDNS.begin("esp32-webserver")) {
    Serial.println("mDNS responder started: http://esp32-webserver.local");
  }

  // Register URI Route Handlers
  server.on("/", handleRoot);
  server.on("/relay/on", []() {
    digitalWrite(RELAY_GPIO, HIGH);
    server.sendHeader("Location", "/");
    server.send(303); // HTTP 303 See Other redirect
  });
  server.on("/relay/off", []() {
    digitalWrite(RELAY_GPIO, LOW);
    server.sendHeader("Location", "/");
    server.send(303);
  });

  server.begin();
  Serial.println("Bare-Metal Socket Server Online [Port 80]");
}

void loop() {
  server.handleClient();
}

MQTT CLOUD TELEMETRY OPTOCOUPLER ISOLATION

Adafruit IO Cloud Telemetry & MQTT Broker Pipelines

Bi-directional asynchronous publish/subscribe messaging engine driving remote high-voltage relay load actuation across global cloud networks.

Assignment Objective & Problem Addressed

Objective: Transition the embedded control plane beyond local firewall boundaries by integrating the ESP32 SoC with Adafruit IO Cloud over the lightweight MQTT (Message Queuing Telemetry Transport) protocol, enabling bi-directional, authenticated actuation of high-voltage 230V AC industrial loads from anywhere in the world.

Problem Addressed: Local web servers (Task 1) cannot be accessed outside the immediate Wi-Fi network without hazardous port-forwarding or public IP exposure. Furthermore, traditional HTTP polling introduces severe network overhead, high latency, and excessive bandwidth consumption. MQTT's publish-subscribe architecture provides persistent, lightweight TCP connections on port 1883 that reduce bandwidth by over 85% and deliver sub-100ms global actuation latency.

MQTT System Topology & Core Actors

  • MQTT Broker: io.adafruit.com (Port 1883) — Centralized cloud message router managing authenticated client connections, routing topics, and maintaining session state.
  • MQTT Publisher: Adafruit IO Web Dashboard & Mobile App — Publishes string command payloads ("ON", "OFF") to the feed when the operator toggles the UI switch.
  • MQTT Subscriber: ESP32 Microcontroller Node — Maintains a persistent TCP keep-alive socket subscribed to topic prajasri/feeds/relay-feed, awaiting asynchronous inbound messages.
  • MQTT Feed / Topic: prajasri/feeds/relay-feed — The hierarchical, addressable message channel decoupling publisher and subscriber, ensuring messages are delivered without direct peer-to-peer coupling.

🛠️ PROBLEMS ENCOUNTERED & ENGINEERING SOLUTIONS (CLICK TO EXPAND) ▼
Problem 1: Optocoupler Active-Low Inversion Logic

The optical relay module utilizes an active-low PNP transistor circuit where setting the pin LOW energized the relay and HIGH de-energized it, causing the AC bulb to turn ON when the cloud dashboard displayed "OFF".

ENGINEERING FIX Abstracted the hardware switching polarity in firmware using #define RELAY_ACTIVE LOW and #define RELAY_INACTIVE HIGH, aligning physical actuation cleanly with cloud dashboard states without circuit alterations.
Problem 2: MQTT Broker Connection Drops via Keep-Alive Timeouts

Blocking delays in the main Arduino loop prevented the ESP32 from dispatching the mandatory 60-second MQTT PINGREQ keep-alive packets, prompting Adafruit IO to abruptly sever the TCP connection.

ENGINEERING FIX Engineered a resilient non-blocking MQTT_connect() reconnection wrapper with automatic retry backoff, and transitioned the subscription listener to non-blocking readSubscription(5000) loops.
💡
Final Learning Reflection: Implementing MQTT demonstrated the profound power of asynchronous publish/subscribe brokers over synchronous HTTP polling. Decoupling the physical ESP32 node from the cloud dashboard through topics allows real-time global telemetry streaming while optical isolation provides absolute galvanic protection against inductive transients and line noise.

ESP32_Adafruit_MQTT_Relay.ino 
#include <WiFi.h>
#include "Adafruit_MQTT.h"
#include "Adafruit_MQTT_Client.h"

#define AIO_SERVER      "io.adafruit.com"
#define AIO_SERVERPORT  1883                   // Unencrypted MQTT port
#define AIO_USERNAME    "YOUR_AIO_USERNAME"    // Adafruit IO Account Username
#define AIO_KEY         "YOUR_AIO_SECRET_KEY"  // Adafruit IO Secret Key
#define RELAY_PIN       5                      // GPIO 5 mapped to Optocoupler trigger

// Inversion logic for Active-LOW optocoupled relay modules
#define RELAY_ACTIVE    LOW
#define RELAY_INACTIVE  HIGH

WiFiClient client;
Adafruit_MQTT_Client mqtt(&client, AIO_SERVER, AIO_SERVERPORT, AIO_USERNAME, AIO_KEY);

// Define topic feed subscription: <username>/feeds/<feed-name>
Adafruit_MQTT_Subscribe relayFeed = Adafruit_MQTT_Subscribe(&mqtt, AIO_USERNAME "/feeds/relay-feed");

// Resilient, non-blocking MQTT reconnection routine
void MQTT_connect() {
  int8_t ret;
  if (mqtt.connected()) return;

  Serial.print("Connecting to Adafruit IO MQTT Broker... ");
  uint8_t retries = 3;
  while ((ret = mqtt.connect()) != 0) { // connect() returns 0 on success
    Serial.println(mqtt.connectErrorString(ret));
    Serial.println("Retrying MQTT connection in 5 seconds...");
    mqtt.disconnect();
    delay(5000);
    retries--;
    if (retries == 0) while (1); // Trap or trigger WDT reset
  }
  Serial.println("MQTT Broker Connected!");
}

void setup() {
  Serial.begin(115200);
  pinMode(RELAY_PIN, OUTPUT);
  digitalWrite(RELAY_PIN, RELAY_INACTIVE); // Ensure load is OFF during boot
  
  WiFi.begin("WIFI_SSID", "WIFI_PASSWORD");
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("\nWi-Fi Connected! IP: %s\n", WiFi.localIP().toString().c_str());

  // Register subscription packet callback
  mqtt.subscribe(&relayFeed);
}

void loop() {
  // Guarantee persistent broker keep-alive handshaking
  MQTT_connect();

  // Non-blocking subscription poll listening for broker publish packets
  Adafruit_MQTT_Subscribe *subscription;
  while ((subscription = mqtt.readSubscription(5000))) {
    if (subscription == &relayFeed) {
      char *payload = (char *)relayFeed.lastread;
      Serial.printf("[Adafruit IO Feed Event] Payload Received: %s\n", payload);

      if (strcmp(payload, "ON") == 0) {
        digitalWrite(RELAY_PIN, RELAY_ACTIVE);
        Serial.println("-> State Transition: High-Voltage Relay CLOSED (Bulb ON)");
      } else if (strcmp(payload, "OFF") == 0) {
        digitalWrite(RELAY_PIN, RELAY_INACTIVE);
        Serial.println("-> State Transition: High-Voltage Relay OPEN (Bulb OFF)");
      }
    }
  }

  // Ping broker periodically to prevent keep-alive timeout drops
  if (!mqtt.ping()) {
    mqtt.disconnect();
  }
}

Important Code Architecture Walkthrough

  • MQTT Client Configuration: Initializes Adafruit_MQTT_Client with persistent TCP socket parameters, credentials, and port 1883 binding.
  • Subscription Registration: Adafruit_MQTT_Subscribe(&mqtt, topic) binds the ESP32 to the specified cloud feed string.
  • Non-Blocking Reconnection: MQTT_connect() checks mqtt.connected() and reconnects with exponential retry backoff without blocking processor cycles.
  • Payload Evaluation Loop: readSubscription(5000) listens for incoming message frames, evaluates lastread against "ON"/"OFF" strings, and shifts hardware GPIO registers.

EVENT-DRIVEN AUTOMATION RESTFUL WEBHOOKS

IFTTT Event Automation & RESTful Webhook Orchestration

Serverless event trigger pipelines bridging external web services, temporal schedulers, and geofences directly to physical hardware actuation.

Assignment Objective & Problem Addressed

Objective: Architect an asynchronous, serverless event-driven automation engine linking IFTTT (If This Then That) cloud triggers with Adafruit IO RESTful APIs and an ESP32 MQTT subscriber node, achieving autonomous electrical load actuation based on temporal cron schedules and external web triggers without microcontroller polling.

Problem Addressed: Embedding complex scheduling algorithms, real-time clock (RTC) hardware synchronization, or third-party web service pollers directly into bare-metal firmware exhausts microcontroller SRAM, creates severe Wi-Fi thread blocking, and requires firmware recompilation for every schedule adjustment. Offloading conditional logic to IFTTT enables zero-overhead serverless orchestration.

IFTTT Automation Paradigm & Webhook Architecture

IFTTT operates on a universal Trigger $\to$ Action event-driven model:

  • Trigger ("If This"): An external temporal event (e.g., cron scheduler set to trigger daily at 10:00 AM) or a third-party service webhook fires automatically within the IFTTT cloud engine.
  • Action ("Then That"): The IFTTT Webhook service formats and dispatches an authenticated HTTP POST request to the Adafruit IO REST API endpoint (https://io.adafruit.com/api/v2/{username}/feeds/{feed_key}/data).
  • Cloud Intermediary Role: Adafruit IO validates the incoming webhook payload, updates the feed record, and immediately broadcasts the updated value to connected MQTT subscribers.
  • Edge Actuation: The ESP32 receives the broker broadcast via its persistent MQTT subscription and actuates the physical relay contacts.

End-to-End Communication Pipeline & Testing

The automation pipeline was rigorously benchmarked under varied operating conditions:

  • Temporal Cron Trigger Testing: Configured fixed-time applets to test scheduled activation; verified average cloud roundtrip latency of $1.4\text{s}$ from IFTTT dispatch to bulb illumination.
  • Manual Webhook Trigger Testing: Dispatched simulated HTTP POST payloads via cURL and Postman to evaluate payload validation and edge actuation repeatability.
  • Wi-Fi Drop & Recovery Resilience: Verified that if the ESP32 briefly loses Wi-Fi, upon reconnection the broker state synchronization immediately pulls the latest feed state.
🛠️ PROBLEMS ENCOUNTERED & ENGINEERING SOLUTIONS (CLICK TO EXPAND) ▼
Problem 1: Adafruit IO Rate-Limiting (HTTP 429 Too Many Requests)

Rapid successive test triggers from IFTTT applets exceeded Adafruit IO's free tier rate limit of 30 data points per minute, causing the broker to reject webhook calls with HTTP 429 status codes.

ENGINEERING FIX Configured minimum cooldown debounce intervals (60 seconds) within the IFTTT applet settings and verified HTTP status codes to prevent request flooding.
Problem 2: Webhook Header & JSON Payload Schema Validation Mismatches

Default IFTTT webhook configurations omitted mandatory authentication headers, prompting Adafruit IO to respond with HTTP 401 Unauthorized and HTTP 400 Bad Request.

ENGINEERING FIX Explicitly serialized required headers (X-AIO-Key: {SECRET_KEY} and Content-Type: application/json) and standardized the JSON payload schema strictly to {"value": "ON"}.
💡
Final Learning Reflection: Decoupled webhook architectures illustrate the core principle of cloud-native IoT: keep edge firmware lean and robust while leveraging serverless cloud engines for complex temporal logic, third-party integrations, and automated decision making.

Problem 1: 1-Wire Timing Collisions Between DHT11 & ESP32 FreeRTOS Wi-Fi Stack

The DHT11 protocol demands microsecond-accurate single-wire bit timing (28–70µs pulses). In early tests, high-priority FreeRTOS Wi-Fi background interrupts preempted the timing loop, corrupting the 40-bit packet and returning persistent nan readings.

ENGINEERING FIX Spaced sensor sampling intervals to 2.5 seconds, implemented a software checksum validator, and wrapped the critical bit-read routines in atomic interrupt-safe execution blocks.
Problem 2: Firebase Auth Token Expiration & Silent Socket Disconnections

Firebase JSON Web Tokens (JWT) expire automatically after 3600 seconds (1 hour). Once expired, subsequent database write attempts failed silently without updating telemetry.

ENGINEERING FIX Enabled Firebase.reconnectWiFi(true) and implemented automated token renewal listeners within Firebase_ESP_Client, ensuring continuous uninterrupted data streaming.

Core Theoretical Foundations: Cloud Computing, Databases & Security

Understanding modern IoT architectures requires mastering the fundamental computer science and cloud infrastructure paradigms that power distributed telemetry:

☁️ Cloud Computing & Platforms FOUNDATION

Cloud Computing is the on-demand delivery of computing services — including servers, storage, databases, networking, and software — over the internet ("the cloud") with pay-as-you-go pricing, eliminating upfront capital expenses for local data centers. A Cloud Platform (e.g., Google Cloud, AWS) provides the unified suite of hardware infrastructure and managed services upon which connected systems run.

🖥️ IaaS vs. PaaS SERVICE MODELS

IaaS (Infrastructure as a Service): Delivers raw, virtualized physical computing resources (virtual machines, block storage, firewalls). The user manages OS, runtimes, and middleware. Examples: AWS EC2, Google Compute Engine.
PaaS (Platform as a Service): Provides a managed runtime environment where developers deploy code without managing underlying operating systems or hardware provisioning. Examples: Heroku, Render, AWS Elastic Beanstalk.

📦 SaaS vs. BaaS MANAGED BACKENDS

SaaS (Software as a Service): End-user applications delivered over a web browser where all code, infrastructure, and data are managed entirely by the vendor. Examples: Google Docs, Microsoft 365, Gmail.
BaaS (Backend as a Service): A category of cloud computing that automates all server-side logic and plumbing — offering turnkey user authentication, real-time databases, push notifications, and cloud storage via client SDKs. Example: Google Firebase, Supabase.

🗄️ Relational (SQL) vs. NoSQL DATA STORES

A Database is an organized collection of electronically stored data. Relational (SQL) systems store data in structured tables with fixed schemas, relations, and strict ACID guarantees (e.g., PostgreSQL, MySQL). NoSQL (Firebase RTDB) organizes data as a dynamic, schema-less JSON tree optimized for horizontal scaling and sub-second bidirectional WebSocket broadcasting to millions of clients.

🛡️ Authentication (AuthN) vs. Authorization (AuthZ) & Dashboard Security SECURITY CRITICAL

In industrial IoT, robust security is critical to prevent malicious or accidental actuator manipulation:

• Authentication (AuthN — "Who Are You?"): The process of verifying a user's or device's identity using credentials (email/password, OAuth token, API secret key, or biometrics). A login system protects the monitoring dashboard by verifying that only designated personnel can open the control plane.

• Authorization (AuthZ — "What Are You Allowed To Do?"): The process of verifying specific access rights and privileges granted to an authenticated entity. In Firebase, this is enforced through Database Security Rules (e.g., public users can .read temperature telemetry, but only authenticated admin accounts can .write to /control/relayState).

ESP32_Firebase_RTDB_Sensors.ino 
#include <WiFi.h>
#include <Firebase_ESP_Client.h>
#include <DHT.h>

#define DHTPIN 4
#define DHTTYPE DHT11
#define LDRPIN 34
#define RELAY_PIN 5

DHT dht(DHTPIN, DHTTYPE);
FirebaseData fbdo;
FirebaseAuth auth;
FirebaseConfig config;

void setup() {
  Serial.begin(115200);
  dht.begin();
  pinMode(RELAY_PIN, OUTPUT);
  WiFi.begin("WIFI_SSID", "WIFI_PASSWORD");
  while (WiFi.status() != WL_CONNECTED) delay(500);

  config.host = "https://your-project-default-rtdb.firebaseio.com";
  config.signer.tokens.legacy_token = "YOUR_DATABASE_SECRET";
  Firebase.begin(&config, &auth);
  Firebase.reconnectWiFi(true);
}

void loop() {
  float temperature = dht.readTemperature();
  float humidity = dht.readHumidity();
  int ambientLight = analogRead(LDRPIN);

  if (!isnan(temperature) && !isnan(humidity)) {
    Firebase.RTDB.setFloat(&fbdo, "/telemetry/temperature", temperature);
    Firebase.RTDB.setFloat(&fbdo, "/telemetry/humidity", humidity);
    Firebase.RTDB.setInt(&fbdo, "/telemetry/lightIntensity", ambientLight);
  }

  // Dual-mode state evaluation: Cloud Override vs Automated Environmental Threshold
  if (Firebase.RTDB.getBool(&fbdo, "/control/manualOverride")) {
    bool manualState = fbdo.to<bool>();
    digitalWrite(RELAY_PIN, manualState ? HIGH : LOW);
  } else {
    // Automated Threshold Actuation: Trigger relay when ambient light drops below threshold
    bool autoState = (ambientLight < 1200);
    digitalWrite(RELAY_PIN, autoState ? HIGH : LOW);
    Firebase.RTDB.setBool(&fbdo, "/control/relayState", autoState);
  }
  delay(2500);
}

LDR Calibration & Hysteresis Automatic Lighting Logic

The ambient light sensor utilizes a 5mm Cadmium-Sulfide (CdS) photoresistor in a voltage divider configuration with a fixed $10\text{k}\Omega$ metal film resistor. The output voltage $V_{out}$ fed into ESP32 GPIO 34 (12-bit ADC) is expressed by:

V_out = V_in × [ R_fixed / ( R_LDR + R_fixed ) ]
Lighting Condition Typical LDR Resistance ADC Output (0–4095) Automated Appliance Decision
Direct Bright Daylight $\approx 1\text{--}2\text{k}\Omega$ $\approx 3200\text{--}3600$ counts RELAY OFF Daylight saturation; lamp disabled
Ambient Room Illumination $\approx 8\text{--}12\text{k}\Omega$ $\approx 1800\text{--}2400$ counts RELAY OFF Sufficient working illuminance
Dark / Twilight Threshold $\ge 35\text{k}\Omega$ $\le 1200$ counts RELAY ACTIVATED Automatic night lamp illumination

Software Hysteresis Guard: To prevent rapid relay chatter and mechanical contact fatigue caused by fluctuating optical shadows near the threshold boundary, a $150\text{--}\text{count}$ hysteresis band is enforced in software: the relay activates when light drops below 1200 counts and only turns off when light rises above 1350 counts.

// Time-Series Telemetry Query & Client-Side CSV Export Utility (RFC 4180 Compliant)
export function exportTelemetryToCSV(telemetryDataset) {
  const headers = [
    "Unix_Timestamp",
    "ISO_DateTime",
    "Temperature_Celsius",
    "Relative_Humidity_Pct",
    "Ambient_Light_ADC",
    "Relay_Actuation_State",
    "Operating_Mode"
  ];

  const csvRows = telemetryDataset.map(record => [
    record.timestamp,
    new Date(record.timestamp).toISOString(),
    Number(record.temperature).toFixed(2),
    Number(record.humidity).toFixed(1),
    record.lightIntensity,
    record.relayState ? "ACTUATED_ON" : "STANDBY_OFF",
    record.mode || "AUTOMATED"
  ]);

  const csvPayload = [headers.join(","), ...csvRows.map(row => row.join(","))].join("\r\n");
  const blob = new Blob([csvPayload], { type: "text/csv;charset=utf-8;" });
  const downloadUrl = URL.createObjectURL(blob);
  
  const link = document.createElement("a");
  link.setAttribute("href", downloadUrl);
  link.setAttribute("download", `ESP32_Telemetry_Report_${Date.now()}.csv`);
  document.body.appendChild(link);
  link.click();
  document.body.removeChild(link);
  URL.revokeObjectURL(downloadUrl); // Free memory buffer immediately
}

#include <WiFi.h>
#include <Firebase_ESP_Client.h>
#include <time.h>

FirebaseData fbdo;
FirebaseAuth auth;
FirebaseConfig config;

// NTP Server settings for synchronized UTC timestamps
const char* ntpServer = "pool.ntp.org";

unsigned long getEpochTime() {
  time_t now;
  struct tm timeinfo;
  if (!getLocalTime(&timeinfo)) return 0;
  time(&now);
  return (unsigned long)now * 1000ULL; // Epoch milliseconds
}

void logTelemetryRecord(float temp, float hum, int light, bool relay, const char* mode) {
  unsigned long timestamp = getEpochTime();
  if (timestamp == 0) timestamp = millis(); // Fallback monotonic time

  String path = "/logs/" + String(timestamp);
  FirebaseJson json;
  json.set("temperature", temp);
  json.set("humidity", hum);
  json.set("lightIntensity", light);
  json.set("relayState", relay);
  json.set("mode", mode);

  if (Firebase.RTDB.setJSON(&fbdo, path.c_str(), &json)) {
    Serial.printf("[Firebase Historical Log Persisted] Key: %s\n", path.c_str());
  } else {
    Serial.printf("[Log Error] %s\n", fbdo.errorReason().c_str());
  }
}
